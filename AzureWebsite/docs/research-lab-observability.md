# Research lab production observability

This runbook describes the metadata-only observability contract for `POST /research-lab/runs`, how to operate it in Azure App Service, and the boundary around exceptional diagnostic content. It is intentionally separate from the product's answer and evidence payloads.

The ordinary telemetry path must remain safe to collect at full fidelity: it contains opaque correlation IDs, bounded counts, durations, status classes, model slugs, and validation categories. It must not contain a query, prompt, source extract, answer, header, cookie, network address, credential, provider payload, or stack trace.

> **Policy gate:** Azure-backed diagnostic content capture is not approved or configured. Do not create a flight-recorder storage resource or enable production content capture until the policy decisions in [Azure-backed capture remains pending](#azure-backed-capture-remains-pending) are approved.

## What the application guarantees

For each accepted or rejected run request, the route creates two independent UUIDs:

- `requestId` identifies the HTTP request.
- `runId` identifies the bounded research execution.

The route binds both IDs to:

- `X-Request-Id` and `X-Research-Run-Id` response headers;
- JSON error responses;
- every line of the NDJSON response stream;
- the harness invocation and every structured stage event;
- the run details shown in the browser UI.

The browser takes the IDs from the response headers and ignores any NDJSON event whose IDs do not match. The harness also records dependency fixtures with both IDs, and replay rejects a fixture that is bound to another run. The in-process run gate releases only the lease for its exact `runId`.

The concurrency gate is per Node.js process. If App Service scales to multiple workers, each worker can accept one run. It is not a distributed global lock.

### Validation language is deliberately narrow

The application does not call a research answer “verified.” These states mean:

| Field | Meaning | What it does **not** mean |
| --- | --- | --- |
| `citationSyntax=valid` | Every detected bracket citation has the expected numeric form. | The citation points to a retrieved source or supports the claim. |
| `referenceValidity=valid` | Every cited number resolves to one of the retrieved evidence items. | The cited passage semantically supports the surrounding sentence. |
| `topicAlignment=mismatch` | The answer has no salient lexical overlap with the question and cited evidence. | A complete factuality judgment. |
| `topicAlignment=aligned` | The answer has enough lexical overlap to avoid the blatant mismatch detector. | Proof of entailment, factual accuracy, or completeness. |
| `semanticSupport=unsupported` | A blatant topic mismatch was detected. | A judgment about every individual claim. |
| `semanticSupport=not_assessed` | No semantic entailment check was performed. | Supported or verified. |

Quick-chat runs use `not_applicable` for all four validation dimensions. Research output with valid reference numbers is still labeled as a research draft, with explicit language that semantic support was not independently assessed. Off-topic output is labeled as an unsupported research draft.

## Ordinary telemetry schema

Each line written by the research observer is a single JSON object with `event=research_lab_stage`. The observer constructs the object from an allowlist and drops unknown properties. Invalid values are omitted. Telemetry write failures are swallowed so monitoring cannot break the request path.

### Required envelope

| Field | Allowed value |
| --- | --- |
| `event` | `research_lab_stage` |
| `requestId` | UUID generated by the route |
| `runId` | UUID generated by the route |
| `stage` | One of the stage names below |
| `status` | `started`, `completed`, `failed`, `limited`, `cancelled`, or `skipped` |

An event is not written unless both IDs, `stage`, and `status` pass validation.

### Optional dimensions

| Field | Allowed values or bound |
| --- | --- |
| `mode` | `quick` or `research` |
| `failureCategory` | Fixed taxonomy described below |
| `modelRequested`, `modelUsed` | A validated provider/model slug, at most 160 characters |
| `httpStatusClass` | Actual client-facing `2xx`, `3xx`, `4xx`, or `5xx`; never a detailed upstream response. A failure after NDJSON headers are flushed remains `2xx` here and is distinguished by `status=failed` plus `failureCategory`. |
| `citationSyntax` | `valid`, `missing`, `malformed`, `not_applicable` |
| `referenceValidity` | `valid`, `incomplete`, `out_of_range`, `not_applicable` |
| `topicAlignment` | `aligned`, `mismatch`, `indeterminate`, `not_applicable` |
| `semanticSupport` | `unsupported`, `not_assessed`, `not_applicable` |

### Optional measurements

| Field | Meaning and bound |
| --- | --- |
| `durationMs` | Stage or request duration, from 0 through 24 hours |
| `queryLength` | Normalized query character count, at most 500 |
| `promptLength` | Constructed prompt character count, at most 50,000 |
| `responseLength` | Normalized answer character count, at most 100,000 |
| `resultCount` | Search or model-catalog result count, at most 1,000 |
| `evidenceCount` | Evidence item count, at most 100 |
| `citationTokenCount` | Detected bracket token count, at most 1,000 |
| `validReferenceCount` | In-range unique reference count, at most 1,000 |
| `streamEventCount` | NDJSON event count, at most 10,000 |
| `streamByteCount` | NDJSON bytes written, at most 10 MiB |
| `promptTokenCount` | Provider-reported prompt tokens, at most 10,000,000 |
| `completionTokenCount` | Provider-reported completion tokens, at most 10,000,000 |
| `totalTokenCount` | Provider-reported total tokens, at most 10,000,000 |

Lengths are measurements, not content. Provider token counts can be absent.

### Stages

| Stage | Typical signal |
| --- | --- |
| `request` | Route admission, terminal outcome, total duration, response class |
| `model_catalog` | Free-model catalog lookup when needed |
| `wikipedia_search` | Search duration, result count, dependency status class |
| `wikipedia_read` | Read duration, evidence count, dependency status class |
| `prompt_construction` | Prompt length, evidence count, mode |
| `model_request` | OpenRouter request duration and status class |
| `model_response` | Response parsing duration, answer length, selected model, usage counts |
| `validation` | Citation, reference, topic-alignment, and semantic-support categories |
| `streaming` | Stream duration, event count, byte count, cancellation or failure |
| `diagnostic_capture` | Whether an anomaly capture was stored, skipped, or rejected; never its content |

### Failure taxonomy and first response

| Category | Meaning | First operator action |
| --- | --- | --- |
| `invalid_input`, `content_type`, `origin_rejected` | Rejected client request | Confirm expected UI/client behavior; do not request the user's content. |
| `rate_limited`, `concurrency_limited` | Local admission control | Review burst rate and active-run duration. Remember the gate is per process. |
| `configuration` | Feature, key, or requested model configuration is unavailable | Check setting **names and deployment state only**. Never print values. |
| `upstream_authentication` | Provider rejected server authentication | Rotate or correct the credential through the approved secret-management path. Do not inspect it in logs or CLI output. |
| `upstream_rate_limited` | Provider returned a rate limit | Compare model and time window; retry only according to policy. |
| `upstream_network`, `upstream_response`, `timeout` | Dependency transport, status, or deadline failure | Identify the first failed dependency stage and compare adjacent runs. |
| `invalid_response` | Dependency returned invalid data or an empty model answer | Reproduce with metadata first; use an approved bounded capture only if essential. |
| `no_evidence` | The bounded Wikipedia search produced no readable extract | Treat as an expected product limitation, not a provider outage. |
| `validation_failed` | Blatant topic mismatch | Confirm the UI labeled the draft unsupported; investigate model quality. |
| `cancelled` | Client disconnected or aborted | Check whether streaming began and how many events were written. |
| `diagnostic_rejected` | Capture was disabled, refused, oversized, or failed | Do not weaken safeguards. Check recorder configuration and policy. |
| `internal` | Unclassified application failure | Correlate stages and deployment version; escalate if repeatable. |

## Privacy and security boundary

Ordinary research telemetry must never contain:

- provider credentials or any other secret;
- authorization, cookie, or proxy headers;
- request or response header collections;
- IP addresses or other network identifiers;
- raw token text or token IDs;
- the query, constructed prompt, source titles or extracts, answer, citations, or qualification text;
- a provider request or response body;
- a stack trace or error message.

The request rate limiter uses a network address as an in-memory key, but the research telemetry does not emit that key. The existing HTTP request logger emits only method, sanitized path, status, and duration; it omits query strings and network addresses.

`AppServiceConsoleLogs` is nevertheless a transport for **all** process standard output and error, not only `research_lab_stage` lines. Kusto filters do not prevent other console lines from being ingested. Before enabling the diagnostic setting:

1. Audit every application `console` write and every library logger reachable in production.
2. Confirm error paths do not serialize request objects, provider objects, response bodies, environment data, or credentials.
3. Keep HTTP logs, detailed error messages, and failed-request tracing out of this observability change. Those sources broaden the data set and can include network or request metadata.
4. Keep reverse-proxy, APM, and platform request/response body capture disabled.
5. Restrict workspace access on the assumption that unrelated application errors may still be present.

Run the repository privacy scan before every deployment. It is a source/artifact check, not proof that every possible runtime exception is safe.

## Safe Azure CLI conventions

- Run `set +x` before Azure work. Never enable shell tracing around Azure commands.
- Never add `--debug` or `--verbose` to commands in this runbook.
- Use a preselected subscription context; do not print access tokens.
- Query only named metadata fields. Never run an unfiltered app-settings or connection-settings listing.
- Use `--output none` for mutations.

## Kusto queries

The queries below expect resource-specific diagnostic routing to `AppServiceConsoleLogs`. They robustly extract a JSON object from `ResultDescription`, discard non-research console lines, and scope by App Service resource ID. Replace the resource-ID placeholder through a workbook resource parameter; do not hard-code a subscription ID into source control.

### Trace one request or run

```kusto
let appResourceId = "<APP_RESOURCE_ID>";
let targetId = "<REQUEST_OR_RUN_ID>";
AppServiceConsoleLogs
| where _ResourceId =~ appResourceId
| extend payload = parse_json(extract(@"(\{.*\})", 1, ResultDescription))
| where tostring(payload.event) == "research_lab_stage"
| extend requestId=tostring(payload.requestId), runId=tostring(payload.runId)
| where requestId == targetId or runId == targetId
| project
    TimeGenerated,
    requestId,
    runId,
    stage=tostring(payload.stage),
    status=tostring(payload.status),
    durationMs=tolong(payload.durationMs),
    failureCategory=tostring(payload.failureCategory),
    httpStatusClass=tostring(payload.httpStatusClass),
    mode=tostring(payload.mode),
    modelRequested=tostring(payload.modelRequested),
    modelUsed=tostring(payload.modelUsed),
    resultCount=tolong(payload.resultCount),
    evidenceCount=tolong(payload.evidenceCount),
    streamEventCount=tolong(payload.streamEventCount),
    topicAlignment=tostring(payload.topicAlignment),
    semanticSupport=tostring(payload.semanticSupport)
| order by TimeGenerated asc
```

The first failed or cancelled stage usually identifies the dependency or phase to investigate. A terminal `request` event gives the overall outcome.

### Run outcomes over time

```kusto
let appResourceId = "<APP_RESOURCE_ID>";
AppServiceConsoleLogs
| where TimeGenerated > ago(24h) and _ResourceId =~ appResourceId
| extend payload = parse_json(extract(@"(\{.*\})", 1, ResultDescription))
| where tostring(payload.event) == "research_lab_stage"
| where tostring(payload.stage) == "request"
| where tostring(payload.status) in ("completed", "failed", "limited", "cancelled")
| summarize runs=count() by bin(TimeGenerated, 5m), status=tostring(payload.status)
| render timechart
```

### Stage latency

```kusto
let appResourceId = "<APP_RESOURCE_ID>";
AppServiceConsoleLogs
| where TimeGenerated > ago(24h) and _ResourceId =~ appResourceId
```


### Validation quality

### Model and token usage

```kusto
let appResourceId = "<APP_RESOURCE_ID>";
AppServiceConsoleLogs
| where TimeGenerated > ago(7d) and _ResourceId =~ appResourceId
| extend payload = parse_json(extract(@"(\{.*\})", 1, ResultDescription))
| where tostring(payload.event) == "research_lab_stage"
| where tostring(payload.stage) == "model_response" and tostring(payload.status) == "completed"
| extend

    modelUsed=tostring(payload.modelUsed),
    durationMs=tolong(payload.durationMs),
    promptTokens=tolong(payload.promptTokenCount),

    runs=dcount(runId),
    p95ResponseMs=percentile(durationMs, 95),
    promptTokens=sum(promptTokens),

```

The free router can select different provider models over time. Group by both requested and used model, and do not assume that `openrouter/free` identifies a stable underlying model.

### Telemetry schema drift

```kusto
let appResourceId = "<APP_RESOURCE_ID>";
let allowed = dynamic([
  "event", "requestId", "runId", "stage", "status", "mode", "failureCategory",
  "durationMs", "queryLength", "promptLength", "responseLength", "resultCount",
  "evidenceCount", "citationTokenCount", "validReferenceCount", "streamEventCount",
  "streamByteCount", "promptTokenCount", "completionTokenCount", "totalTokenCount",
  "modelRequested", "modelUsed", "httpStatusClass", "citationSyntax",
  "referenceValidity", "topicAlignment", "semanticSupport"
]);
AppServiceConsoleLogs
| where TimeGenerated > ago(24h) and _ResourceId =~ appResourceId
| extend payload = parse_json(extract(@"(\{.*\})", 1, ResultDescription))
| where tostring(payload.event) == "research_lab_stage"
| extend unexpected=set_difference(bag_keys(payload), allowed)
| where array_length(unexpected) > 0
| project TimeGenerated, requestId=tostring(payload.requestId), runId=tostring(payload.runId), unexpected
```

Any new field must receive a privacy review and an update to both the application allowlist and this query. Do not simply silence the alert.

| Panel | Visualization | Purpose |
| --- | --- | --- |
| Run outcomes | Stacked time chart | Completed, failed, limited, and cancelled terminal requests |
| Failure categories | Bar chart plus table | Highest-volume failure classes and affected run counts |
| Stage latency | Table or bar chart | p50/p95/max duration by stage |
| Dependency health | Time chart | Wikipedia search/read and model request failures, timeouts, and status classes |
| Reference checks, not semantic verification | Matrix | Citation syntax, reference validity, topic alignment, semantic support |
| Model routing | Table | Requested versus provider-used model, run count, response latency |
| Usage | Time chart | Prompt and completion tokens; missing usage is a separate count |
| Stream health | Table | Completed/failed/cancelled streams, event/byte counts, duration |
| Admission controls | Time chart | Local rate and concurrency limits |
| Correlation lookup | Text parameter and table | Ordered events for one request or run ID |
| Telemetry freshness | Tiles | Last event time, total stage events, distinct runs |
| Schema drift | Alert-style table | Unexpected keys in `research_lab_stage` payloads |

Do not include raw `ResultDescription` in a workbook panel. Do not add a prompt/answer search box. Workbook export, sharing, and download permissions should be limited to operators with an incident need.

## Alerts

Start with the following thresholds, then tune them after at least 14 days of real volume. “Runs” refers to distinct `runId` values where possible.

| Condition | Initial window and threshold | Severity | Action |
| --- | --- | --- | --- |
| Unexpected telemetry field | Any event in 5 minutes | 1 | Stop rollout or disable the feature if a sensitive field could be present; preserve metadata-only evidence. |
| Upstream authentication or configuration failure | Any terminal run in 5 minutes | 1 | Check deployment/configuration through the secret-management path. |
| Internal failure | Any terminal run in 5 minutes | 2 | Correlate stages and deployment version. |
| Topic mismatch | Any validation failure in 15 minutes | 3 | Confirm the UI labeled output unsupported; open a quality investigation. |
| Failure rate | More than 25% with at least 5 runs in 15 minutes | 2 | Break down by stage and failure category. |
| Dependency timeout/network burst | At least 3 runs in 15 minutes | 2 | Compare dependency stages and provider status. |
| Admission-control burst | At least 5 limited requests in 15 minutes | 3 | Review traffic and long-running requests before raising concurrency. |
| Total request p95 | More than 45 seconds with at least 5 completed runs in 30 minutes | 3 | Locate the dominant stage; do not increase deadlines first. |

Do not alert on “no research telemetry” unless an approved synthetic run is scheduled. Organic traffic can legitimately be zero, and the current application has no content-free research readiness probe.

No action group exists in the pre-change snapshot. Approve the on-call destination and escalation policy before creating one. Do not pass a personal address or signed webhook URL on the command line. Create the receiver through approved secure IaC or the portal, then capture only its resource ID into `AZ_ACTION_GROUP_ID`.

```sh
| project TimeGenerated'

az monitor scheduled-query create \
  --resource-group "$AZ_RESOURCE_GROUP" \
  --name research-lab-topic-mismatch \
  --location "$AZ_MONITOR_LOCATION" \
  --scopes "$AZ_APP_ID" \
  --severity 3 \
  --evaluation-frequency 5m \
  --window-size 15m \
  --condition "count 'TopicMismatch' > 0" \
  --condition-query "TopicMismatch=$AZ_TOPIC_MISMATCH_QUERY" \
  --action-groups "$AZ_ACTION_GROUP_ID" \
  --description 'Research answer failed the blatant topic-alignment check.' \
  --output none
```

Do not use `--skip-query-validation`. Validate the query against real metadata-only events before enabling the rule. Apply the same pattern to the other alert queries after reviewing thresholds and on-call routing.

## Sampling and retention

### Ordinary stage events

Keep 100% of `research_lab_stage` events for the initial 14-day calibration period. The bounded run gate and request limiter constrain volume, and complete stage sequences are more useful than independently sampled fragments.

If cost later requires sampling, implement and test deterministic **whole-run** sampling keyed by `runId`:

- retain every event for failed, cancelled, limited, mismatch, configuration, authentication, and schema-drift runs;
- sample only normal completed runs;
- make all stages of a sampled run share the same decision;
- emit the configured sampling rate as deployment metadata, not user-controlled input;
- update workbook denominators and alert thresholds.

Do not independently sample individual stages. Do not add an ingestion transformation that keeps content-bearing console lines while discarding the safe structured events.

### Retention

| Data | Initial retention | Maximum without a new approval |
| --- | --- | --- |
| `AppServiceConsoleLogs` workspace/table | 30 days | 30 days |
| Summary-only local anomaly capture | 1 hour by default | 24 hours enforced by code |
| Content-bearing local anomaly capture | 1 hour by default, explicit opt-in only | 24 hours enforced by code |
| Azure-backed content capture | Not configured | Not approved |

Review ingestion volume and incident usefulness after 14 days, then review retention quarterly. Longer retention needs a documented purpose, cost estimate, and privacy approval.

## RBAC

Use separate roles for setup and daily operation:

- Monitoring infrastructure maintainers: `Monitoring Contributor` only at the App Service and monitoring-resource scope needed to manage diagnostic settings and alerts. Pair it with the narrow workspace-management permission needed for retention. Avoid subscription-wide `Contributor` or `Owner`.
- On-call readers: `Log Analytics Reader` or a narrower custom/data-reader role scoped to the dedicated workspace/table, plus `Monitoring Reader` for alert state.
- Application deployment identity: no workspace data-read role. Azure's diagnostic pipeline writes resource logs; the App Service system-assigned identity does not need broad Log Analytics access for this design.
- Workbook viewers: read access only; no export or sharing role unless operationally required.
- Diagnostic-content custodians: a separate, smaller group if Azure-backed capture is ever approved. Ordinary workspace readers must not automatically receive content-capture access.

Use groups rather than direct user assignments, time-bound elevation where available, access reviews, and break-glass auditing. Review role assignments quarterly and after every incident involving captured content.

## Operator workflow

1. Ask the reporter for the displayed `requestId` or `runId`, approximate time, and visible error category. Do not ask them to paste the prompt or answer into a ticket.
2. Run the correlation query and confirm both IDs stay constant through the route, stream, and stages.
3. Find the first `failed`, `cancelled`, or `limited` event. Use the failure category, duration, status class, counts, and model metadata.
4. Compare nearby runs by the same stage and model to distinguish a one-off run from a provider or deployment incident.
5. For validation incidents, keep citation syntax, reference validity, topic alignment, and semantic support separate. Confirm the UI did not present an unsupported answer reassuringly.
6. Reproduce with a non-sensitive synthetic input in a local or approved staging environment. Free-router model selection can change, so record both requested and used model slugs.
7. Escalate to diagnostic capture only when metadata cannot answer a concrete incident question and capture was approved **before** the run. Never turn capture on retrospectively for general exploration.
8. If a valid content capture exists, move it only through the approved private incident path, replay it offline, and avoid copying its contents into chat, tickets, email, or build artifacts.
9. Remove the exact capture through the approved disposal process after replay or expiry. Verify that no copy remains in a shell history, download folder, CI artifact, or ticket.
10. Close with the request/run IDs, failure category, affected time window, fix, and metadata-only evidence. Record whether validation was local, Azure read-only, or deployed-production verification.

```sh
AZ_RESEARCH_BASE_URL='https://cvkewebsite.azurewebsites.net'

curl --silent --show-error \
```

## Local diagnostic recorder and replay

The diagnostic recorder is disabled by default. Enabling capture alone does not enable content; content requires a second explicit flag. In production, the application refuses the local file store and remains disabled unless an approved private store is injected.

The local store enforces:

- an explicit absolute directory outside the public web root;
- directory mode `0700` and file mode `0600`;
- 64 KiB default and 256 KiB hard per-capture limits;
- 25 default and 100 hard retained files;
- 1-hour default and 24-hour hard expiry;
- allowlisted anomaly categories only: invalid model response, replay divergence, and topic mismatch;
- recursive size/depth bounds and credential-pattern redaction;
- exact-secret replacement using the configured provider credential;
- UUID schema checks and refusal of symlinks or oversized files on replay.

Redaction is defense in depth, not proof that content is non-sensitive. A query, source excerpt, or answer can contain private information without looking like a credential.

### Local-only opt-in

Use a private ignored directory, a restrictive umask, and development mode. Never use this configuration on App Service:

```sh
umask 077
mkdir -p .private-research-captures
export NODE_ENV=development
export RESEARCH_LAB_DIAGNOSTIC_CAPTURE_ENABLED=true
export RESEARCH_LAB_DIAGNOSTIC_CONTENT_ENABLED=true
export RESEARCH_LAB_DIAGNOSTIC_DIRECTORY="$(pwd)/.private-research-captures"
```

With content disabled, the recorder stores only the bounded summary and the capture cannot be replayed. With content enabled, anomaly captures can contain the normalized query, dependency fixtures, provider response, evidence, and expected outcome; treat the file as sensitive.

Replay one exact, unexpired capture:

```sh
npm run research:replay -- .private-research-captures/<CAPTURE_ID>.json
```

Replay is deterministic and offline: it supplies recorded Wikipedia/model fixtures to the harness, refuses unexpected or unused dependency calls, verifies that every fixture has the capture's request/run IDs, and compares the resulting bounded summary with the recorded expected summary. Its console output contains correlation IDs, category, dependency count, outcome, and validation metadata—not prompt or answer content.

Expired captures are refused. The local store prunes expired, corrupt, oversized, and excess files before a subsequent write; operators must still use the approved disposal process when an incident closes before the next write.

## Azure-backed capture remains pending

The code provides a storage abstraction, but no Azure content store is configured. Do not use Log Analytics, application console logs, or an ordinary blob container as an ad hoc flight recorder.

Approval must settle all of the following before implementation:

- whether production prompt/answer/source capture is permitted at all;
- the precise anomaly categories and minimum data fields;
- user notice or consent requirements;
- data classification, residency, legal-hold, and deletion requirements;
- the maximum TTL, object count, and byte budget, no greater than the application hard limits without a code review;
- Microsoft Entra groups allowed to read, replay, or delete captures;
- whether platform-managed encryption is sufficient or a customer-managed key is required;
- private networking, firewall, public-access, and data-exfiltration controls;
- use of the App Service managed identity without shared keys or signed URLs;
- immutable access/audit logs and an incident-ticket access reason;
- automated lifecycle deletion plus verification of deletion;
- how redaction failures trigger immediate disablement and incident response.

After approval, wire the existing managed-identity Blob adapter to a dedicated private container, add lifecycle/RBAC integration tests, perform a threat review, and deploy it separately. Production content capture must remain off until that review is complete.

### Local validation

- Run `npm run check` from the nested application directory.
- Run the correlation, redaction/privacy, failure-classification, topic-mismatch, concurrency/run-binding, replay, and secret-leakage tests.
- Inspect the exact diff and untracked files.

- Re-run the metadata-only CLI inspection.
